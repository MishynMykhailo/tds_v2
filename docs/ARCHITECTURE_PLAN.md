# Backend Rewrite — Целевая структура (v2, разведка завершена)

> Статус: план структуры. Переписывание кода ещё НЕ начато. Разведка по
> composer-зависимостям, карте зависимостей между модулями `Component/*` и
> схеме БД завершена — факты ниже подтверждены чтением реального кода/vendor,
> не догадки.

## Контекст: зачем это делается

Текущий бэкенд (`application/`) — это декомпилированный из ionCube-байткода PHP,
восстановленный автоматическим инструментом (см. [`../default/BUG_PATTERNS.md`](../default/BUG_PATTERNS.md)).
За сессию отладки 2026-08-27 найдено и исправлено ~40+ системных багов
декомпиляции по 14 каталогизированным паттернам (инвертированные ветки if/else,
`self::` вместо `parent::`, потерянные `use()` в замыканиях, неверные касты и
т.д.) — включая баг в `MacrosProcessor.php`, найденный и исправленный уже после
основной сессии. Сайт сейчас РАБОТАЕТ, но это результат точечных фиксов поверх
кода, который никогда не предназначался для чтения человеком.

**Решение пользователя:** полностью переписать весь бэкенд на чистом,
читаемом PHP — целиком, одним проектом (не по модулям с параллельным
роллаутом). Смена клик-роутинга на Go — отдельная, более поздняя задача,
не входит в этот проект.

## Что переносится, а что нет

- **Язык:** остаётся PHP (не Go — это отдельный будущий трек только для
  хот-пути обработки клика, см. [`../frontend/architecture_plan.md`](../frontend/architecture_plan.md)
  для параллельного трека переписывания фронтенда на React).
- **Бизнес-логика:** ПОВТОРЯЕТСЯ, а не придумывается заново. Источник истины
  о том, "как это должно работать по факту" — уже стабилизированное поведение
  из `docs/default/FIXES_LOG.md`, `docs/default/BUG_PATTERNS.md`,
  `docs/frontend/backend_api_reference.md` и QA-находок в `docs/frontend/round*_findings.md`.
  Тестов в проекте нет вообще — эти документы сейчас ЕДИНСТВЕННАЯ спецификация
  ожидаемого поведения.
- **Внешний контракт не меняется:** публичные трекинговые ссылки (`?object=...`
  для админки, короткие алиасы кампаний типа `/qbrtcz2`) должны продолжать
  работать один в один — фронтенд (отдельный React-проект) и уже настроенные
  кампании клиента не должны почувствовать разницу.
- **БД:** переиспользуется существующая схема/данные, а не создаётся с нуля.
  Подтверждено: `migrations2/` (219 файлов, `YYYYMMDDHHMMSS_описание.php`,
  диапазон 2016-09-09 — 2021-08-27) — единственная АКТИВНАЯ схема
  (`MigrationsRepository.php` жёстко указывает на этот путь). `migrations/`
  (102 файла, `0001.php`...`0102.php`) — замороженный legacy-набор, используется
  только отдельным `LegacyMigrationsController`/`MigrationsRunLegacyCommand`.
  Не двусмысленность — просто исторический долг, `migrations2/` читаем как
  единый источник правды о структуре БД.

## Что уже есть в vendor/ и что это значит для рewrite

Проверено по `vendor/composer/installed.json` (64 пакета) — фреймворка нет,
но кое-что полезное уже подключено:

- **Роутинг:** `altorouter/altorouter` — простой, но не PSR-совместимый роутер.
  Можно оставить или заменить на `nikic/fast-route` (более активно
  поддерживается) — решение отложено до дизайн-фазы.
- **DI-контейнер: ОТСУТСТВУЕТ вообще** (ни `php-di/php-di`, ни
  `symfony/dependency-injection`) — это придётся добавить новой зависимостью,
  такова цена ухода от 2122 вызовов `::instance()`.
- **HTTP:** `guzzlehttp/guzzle` 6.5.5 + `guzzlehttp/psr7` + `psr/http-message` +
  `laminas/laminas-diactoros` — PSR-7 уже есть, новый Http-слой строится на этом,
  не с нуля.
- **БД:** `adodb/adodb-php` 5.20.18 — низкоуровневая абстракция под текущими
  `Core/Db`/`Core/TdsDb`. ORM нет (Doctrine присутствует только как
  вспомогательные `doctrine/cache`+`doctrine/instantiator`, не полноценный ORM).
- **Тесты: `phpunit/phpunit` 6.5.14 уже завезён в vendor, но НЕ используется
  нигде** — ни одного реального тест-сьюта поверх него. Для нового проекта
  версия 6.5 (2017 года) сильно устарела — рекомендуется поднять до актуальной
  PHPUnit 10/11 отдельной зависимостью, а не переиспользовать эту.
- Также есть: `monolog` (логирование), `firebase/php-jwt`, `piwik/device-detector`,
  `ip2location/ip2location-php`, `vlucas/valitron` (валидация), `spiral/roadrunner`
  + `spiral/goridge` (текущий апп-сервер рантайм — переносится как есть).

## Итоговое архитектурное решение (после дебатов 3 агентов + фактчека)

Проведён спор "Laravel+Octane целиком" vs "лёгкий кастомный PSR-7-стек
целиком" + независимый фактчек по ionCube-совместимости и паттернам установки
у конкурентов (Keitaro, Binom, коммерческие Laravel-скрипты). Ни один подход
не выигрывает целиком — решение: **разделить по той же линии, по которой
позже будет резаться Go**.

**1. Админка (все 51 CRUD-модуля: Campaigns, Offers, Users, Reports, ...)
→ Laravel + Laravel Octane на RoadRunner.**
- RoadRunner уже куплен как зависимость (`spiral/roadrunner`+`goridge`,
  `.rr.yaml`) — Octane просто использует то, что уже есть.
- Реалистичная память на прогретый воркер — десятки МБ, не гигабайты
  (страх "10-20ГБ" был багом `Db::instance()`, а не свойством фреймворка).
- DI-контейнер, миграции, очереди на Redis, Artisan-команды, тестовый
  каркас — всё то, чего сейчас нет вообще, получаем без сборки с нуля.
- Домен+SSL: тривиально (nginx терминирует TLS, `TrustHosts`+`TrustProxies`
  middleware, сессии не прибиты к домену по умолчанию).

**2. Traffic-пайплайн (обработка клика — бот-детект, матчинг стримов,
рендер лендингов) → лёгкое PSR-7-ядро БЕЗ Eloquent/Facades/автосвязывания.**
- Это самый нагруженный по RPS путь — минимум абстракций = минимум накладных
  расходов на запрос, независимо от того, насколько эффективен Octane.
- Уже физически изолирован процессом RoadRunner/Goridge — при будущем
  переезде на Go меняется именно этот воркер, Laravel-часть не трогается.
- Ключевая практическая причина, подтверждённая фактчеком (см. ниже) —
  ionCube-кодирование ГОРАЗДО проще и надёжнее для кода без активного
  reflection/DI-автосвязывания, а это как раз код горячего пути.

**Почему не "всё на Laravel" и не "всё на лёгком стеке":**
- Фактчек подтвердил: `ionCube` **ломает reflection у DI-контейнеров по
  умолчанию** (`ReflectionParameter::getDefaultValue()` не работает на
  закодированных классах) — это НЕ блокер (есть флаг `--allow-reflection-all`
  + официальный гайд ionCube "как кодировать Laravel"), но это означает
  **ручную поддержку exclusion-листов при каждом релизе** для Laravel-части.
  Держать самый нагруженный/часто мутирующий код (клик-пайплайн) вне этой
  возни — практично.
- "Всё на лёгком стеке" означало бы заново собирать замену Eloquent/Artisan/
  Queue руками — то есть повторение исходной ошибки проекта (самодельный
  необслуживаемый каркас), только более аккуратными кубиками.

## Установка и защита прод-билда

Подтверждено фактчеком по реальным конкурентам:
- **Keitaro** ставится через собственный bash CLI (`kctl`), не веб-визард;
  домен+SSL — `kctl` сам гоняет certbot после того, как admin направил A-запись.
- **Binom v2** — классический bash install-скрипт на голом VPS.
- Коммерческие Laravel-скрипты (CodeCanyon) с ionCube — типовое разделение:
  **кодируется** прикладной код (`app/`-классы, контроллеры); **НЕ
  кодируется** `.env`, конфиги, Blade-шаблоны (ionCube физически не может
  кодировать `.blade.php` — фреймворк должен видеть исходный Blade-синтаксис),
  `storage/`/загрузки; `vendor/` (сторонний опенсорс) кодировать бессмысленно.

**Рекомендуемый пайплайн для этого проекта:**
1. Dev-репозиторий — обычный читаемый код, только у владельца.
2. Билд-скрипт: `composer install --no-dev --optimize-autoloader` →
   ionCube Encoder по `app/` (Laravel-часть, с `--allow-reflection-all` +
   exclusion-лист для хелперов/Facade-магии) и по traffic-ядру (базовые
   настройки, там reflection почти не используется) → Blade-шаблоны,
   `.env.example`, nginx-конфиг, папка лендингов остаются НЕЗАКОДИРОВАННЫМИ.
3. bash-установщик (по образцу `kctl`/Binom, не веб-визард — целевой
   пользователь уже комфортно работает с VPS/Docker): спрашивает домен → сам
   гоняет certbot → пишет `.env` → миграции → systemd-юниты (Octane-воркер,
   traffic-воркер, queue-воркер, scheduler).
4. Результат: сторонний человек на сервере видит закодированный
   (нечитаемый) PHP, открытый редактируемый `nginx.conf`, и открытую папку
   лендингов — ровно как запрошено.

## Проблемы текущей архитектуры, которые новая структура обязана устранить

1. **2122 вызова `SomeService::instance()`** по всему коду — глобальное
   состояние через синглтоны, DI-контейнера нет вообще. Новая структура
   обязана внедрять зависимости явно (конструктор/контейнер), а не через
   статические синглтоны.
2. **Две параллельные системы миграций** (`migrations/` и `migrations2/`) —
   объединяются в одну.
3. **Нет автоматических тестов** — новая структура пишется с юнит- и
   интеграционными тестами с первого дня, не постфактум.
4. **Смешение слоёв** — сейчас `Component/*` (бизнес-модули) напрямую мешают
   HTTP-диспетчинг, доступ к БД и бизнес-правила в одном классе-контроллере.
   Новая структура разделяет это на слои (см. ниже).
5. **Мёртвый/анти-пиратский код** — лицензионные заглушки (`LicenseService`,
   `_securityCheck()` с `return;` в начале, захардкоженный `FeatureService`)
   не переносятся как есть — либо удаляются, либо переосмысляются как
   простая feature-flag система без псевдо-лицензирования.
6. **`Core/` не является чистым фундаментом** — подтверждено: 26 файлов в
   `Core/` напрямую ссылаются на `Component\*` (например, `ComponentManager`
   и 6 `Cache*`-обработчиков событий в `Core/EntityEventManager/EventHandler/`
   жёстко зовут `Component\Campaigns\Repository\CampaignRepository::instance()`
   и аналоги для Streams/Domains/StreamFilters/TrackerInfo напрямую). Это
   архитектурный смысл "плагинного" дизайна оригинала, но в новой структуре
   `Domain`/`Infrastructure`-слой не должен знать о конкретных модулях —
   такие связи заменяются на события/интерфейсы, определённые в самом
   фундаменте, а не жёстко зашитые обращения наружу.

## Предлагаемая целевая структура каталогов

```
src/
├── Domain/                    # Чистая бизнес-логика, без зависимости от HTTP/БД
│   ├── Campaigns/
│   │   ├── Campaign.php               (Entity)
│   │   ├── CampaignRepositoryInterface.php
│   │   └── Rules/                     (доменные правила: uniqueness TTL и т.д.)
│   ├── Streams/
│   │   ├── Stream.php
│   │   ├── StreamFilters/
│   │   └── StreamActions/              (Redirect, LocalFile, ShowOffer, ...)
│   ├── Offers/
│   ├── Landings/
│   ├── TrafficSources/
│   ├── Macros/                         (чистая логика MacrosProcessor, без Sandbox)
│   ├── Clicks/                         (RawClick как Value Object)
│   └── ... (остальные — всего 51 модуль сейчас в Component/*)
│
├── Application/                # Use-case сервисы, оркестрируют Domain + Infra
│   ├── Campaigns/CreateCampaign.php, UpdateCampaign.php, ...
│   ├── ClickHandling/ProcessClickUseCase.php   (замена текущего Traffic-пайплайна)
│   └── ...
│
├── Infrastructure/              # Технические детали
│   ├── Db/                      (реализации *RepositoryInterface через MySQL)
│   ├── Cache/                   (Redis/файловый кэш)
│   ├── Sandbox/                 (CGI/FastCGI-исполнение пользовательских .php-лендингов —
│   │                             переносится с минимальными изменениями, это рабочий механизм)
│   ├── Http/                    (PSR-7 запрос/ответ, замена Traffic\Request\ServerRequest)
│   └── DependencyInjection/     (контейнер вместо ::instance())
│
├── Interface/                   # Точки входа
│   ├── Admin/Http/               (контроллеры админки, замена Admin\Controller\*)
│   ├── Traffic/Http/             (обработчик кликов, замена index.php + TrafficRouter)
│   └── Console/                  (cron/console-команды, замена Cron\*)
│
└── Migrations/                   # Единая система миграций (замена migrations/ + migrations2/)

tests/
├── Unit/           (Domain-логика — правила стримов, макросы, валидация)
└── Integration/     (Application use-cases против тестовой БД)
```

## Порядок реализации внутри "одного проекта"

Даже при подходе "весь бэкенд одним проектом" код физически придётся писать в
каком-то порядке — снизу вверх по зависимостям:

1. **Infrastructure-фундамент**: Db-слой, DI-контейнер, HTTP-кернел (PSR-7 на
   базе уже имеющегося `laminas-diactoros`), конфиг, единая система миграций
   (на основе `migrations2/`).
2. **"Модули-хабы"** — подтверждено разведкой по количеству реальных ссылок из
   других модулей (`grep -rl "Component\\ИмяМодуля\\"`): **Console (51
   зависящих файла), Cron (34), Users (30), Campaigns (27), Grid (16),
   Streams (15), PruneTask (15), DelayedCommands (15), Clicks (14)**. Console
   и Cron выше всех, потому что почти каждый модуль регистрирует свои
   консольные команды/крон-задачи через базовые классы, живущие там — значит
   в новой структуре база для console-команд и cron-задач должна быть готова
   ДО переноса большинства остальных модулей, наравне с Users (авторизация)
   и Campaigns (центральная сущность, на которую ссылаются Streams/Clicks/Reports).
3. **Traffic-пайплайн** (обработка клика) — самый критичный по бизнес-ценности
   путь, переносится с явной проверкой один-в-один против `docs/default/FIXES_LOG.md`.
4. **Admin CRUD-модули** — оставшиеся Component-модули (из 51 — по мере
   готовности инфраструктуры под ними), от менее связанных к более связанным.
5. **Cron/консольные команды, использующие модули** — сама база (см. п.1)
   переносится рано, но конкретные задачи (`PruneTask`, `DelayedCommands` —
   тоже в топе хабов, 15 ссылающихся файлов каждый) — по мере готовности того,
   что они обслуживают.

## Верификация соответствия старому поведению

Поскольку тестов не было и новая система пишется "с нуля" по чтению старого
кода — единственный способ гарантировать отсутствие регрессий:
- Для каждого перенесённого модуля — сверять поведение живым Playwright-тестом
  против СТАРОГО приложения (оставленного работать параллельно на другом порту)
  и НОВОГО, сравнивая ответы API один в один.
- Использовать уже написанные QA-сценарии как готовый набор регрессионных
  проверок — конкретный список:

| Документ | Что покрывает |
|---|---|

| `docs/default/BUG_PATTERNS.md` (356 строк) | 14 паттернов декомпиляционных багов с эвристиками поиска |
