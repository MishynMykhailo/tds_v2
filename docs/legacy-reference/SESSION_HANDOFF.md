Дата: 2026-08-27. Этот файл — сводка ВСЕГО, что сделано за длинную сессию
отладки, чтобы новый чат мог продолжить без повторного анализа с нуля.
Читать ЭТОТ файл первым, потом при необходимости остальное в этой же папке
`docs/` — `BUG_PATTERNS.md` (детальный список багов декомпиляции),

Отдельно, в КОРНЕ проекта (не в `docs/`) — `HAND_FIX.md`: инструкция по
вещам, которые нужно сделать руками (не через код), например — куда
класть скачанные GeoDB-базы.

## 0. ВАЖНАЯ ТЕХНИЧЕСКАЯ ЛОВУШКА — путь к проекту

Имя папки проекта содержит СКРЫТЫЙ неразрывный пробел (U+00A0) перед тире:
`tds_source-main<NBSP>— without KT`. Если печатать путь вручную с обычным
пробелом, инструменты Read/Write/Edit создадут/откроют файл в ДРУГОЙ,
несуществующей папке-двойнике (это уже случалось несколько раз в сессии).

**Правило: всегда работать через Bash с ОТНОСИТЕЛЬНЫМИ путями** (текущая
директория сессии уже указывает на правильную папку) — `cat file.php`,
`python3 -c "... open('application/...', ...)"`, `sed -i ... file.php` и
т.д. НЕ использовать Read/Write/Edit с абсолютным путём, если только
абсолютный путь не был явно скопирован из системного вывода этого чата.

## 1. Что это за проект

Купленный у фрилансера open-source TDS (Traffic Distribution System) —
похож по структуре на Keitaro, но НЕ Keitaro (пользователь подтвердил).
Версия 9.13.9. PHP 7.2-7.4, свой мини-фреймворк, MySQL, опционально
RoadRunner. Подробности — `PROJECT_AS_DELIVERED.md`.

**Ключевая находка о природе проекта:** это НЕ обычный "плохо написанный"
код — это исходник, **декомпилированный из закодированного ionCube-байткода
обратно в читаемый PHP** каким-то автоматическим инструментом (не
фрилансером — судя по всему, ещё раньше). Инструмент декомпиляции оставлял
систематические артефакты — это и есть подавляющее большинство всех
багов, найденных в сессии. Полная таксономия (12+ классов багов с
примерами) — в `BUG_PATTERNS.md`.

### Этап B — поднятие Docker-стенда и полная отладка runtime
Пользователь попросил поднять проект в Docker и создать админа. По ходу
выяснилось, что кода "с виду ОК" НЕДОСТАТОЧНО — декомпилированный код не
запускался вообще. Прошли длинный цикл: запуск → фатал → чиним → запуск →
следующий фатал → чиним, десятки раз, вручную и через параллельных
агентов (форки).

**Итог: сайт и админ-панель РАБОТАЮТ.** Логин подтверждён вживую через
реальный HTTP (не только тестовыми скриптами).

## 3. Текущее состояние Docker-стенда (уже поднято, не пересоздавать)

```
docker ps:
  tds-app    (image tds-app-dev, live bind-mount ./ -> /app, порт 8090->8080)
  tds-mysql  (mysql:5.7, база tds, юзер/пароль tds/secret, схема+данные залиты)
```
Сеть: `tds-net`. Доступ из браузера пользователя: **http://localhost:8090/admin/**
Логин: `admin` / `TdsAdmin2026!` (создан через `bin/cli.php admins:create`).

Технические детали стенда (если контейнеры вдруг умрут и нужно поднять
заново):
- `Dockerfile.dev` в корне проекта — php:7.4-cli + нужные расширения
  (pdo_mysql, mysqli, zip, gd, mbstring, sockets, bcmath), НЕ использует
  composer install (в проекте нет composer.json, vendor/ уже полностью
  на месте) и НЕ использует RoadRunner (в проекте отсутствовал бинарник
  и конфиг `.rr.yaml`) — вместо этого встроенный PHP-сервер
  `php -S 0.0.0.0:8080 router.php`.
- `router.php` в корне — простой роутер для встроенного PHP-сервера,
  имитирует правила .htaccess (статика напрямую, всё остальное — в
  `admin/index.php` или корневой `index.php`).
- `application/config/config.ini.php` — секция `[db]` указывает на
  `server=tds-mysql, user=tds, password=secret, name=tds, prefix=tds_`
  (уже изменено под текущий Docker-стенд, ЭТО НЕ оригинальные значения
  из поставки).
- Пересоздать контейнеры (если нужно):
  ```
  docker network create tds-net   # если ещё нет
  docker run -d --name tds-mysql --network tds-net --platform linux/amd64 \
    -e MYSQL_ROOT_PASSWORD=secret -e MYSQL_DATABASE=tds \
    -e MYSQL_USER=tds -e MYSQL_PASSWORD=secret -p 3306:3306 mysql:5.7
  # подождать готовности, затем:
  docker exec -i tds-mysql mysql -uroot -psecret tds < application/data/schema.sql
  docker exec -i tds-mysql mysql -uroot -psecret tds < application/data/data.sql
  docker build -f Dockerfile.dev -t tds-app-dev .
  docker run -d --name tds-app --network tds-net -p 8090:8080 \
    -v "$(pwd):/app" -w /app tds-app-dev
  ```
- Логи: `docker exec tds-app cat var/log/PRODUCTION-2026-08-26.log` (или
  свежая дата) — там реальные ошибки уровня приложения (не PHP-warning про
  голые константы, которые ещё остались в незачищенных 30 файлах и
  безобидны).
- Логи веб-сервера (реальные HTTP-запросы браузера, полезно для отладки
  "что реально шлёт браузер"): `docker logs tds-app --since 20m`.

**Как проверять фикс вручную (без браузера), рабочий шаблон:**
```bash
docker run --rm --network tds-net curlimages/curl:latest sh -c '
curl -sS -c /tmp/cookies.txt -X POST "http://tds-app:8080/admin/?object=auth.login" \
  -H "Content-Type: application/json" \
  -d "{\"login\":\"admin\",\"password\":\"TdsAdmin2026!\"}" -o /dev/null
curl -sS -b /tmp/cookies.txt "http://tds-app:8080/admin/?object=НУЖНЫЙ_ЭКШН" -w "\nHTTP:%{http_code}\n"
'
```
Фронтенд общается через `?object=контроллер.экшн` (иногда POST с JSON-телом
как в примере логина) и пачками через `POST /admin/?bulk` (массив
`[{"params": {...}}]`).

## 4. Как чинили баги — методология (пригодится для новых)

1. Взять сообщение из консоли браузера пользователя (обычно
   `POST .../admin/?object=X.Y 500` + стектрейс app.js — сам JS не даёт
   деталей, важен только сам факт и endpoint).
2. Смотреть `docker exec tds-app cat var/log/PRODUCTION-*.log | grep -v
   "undefined constant" | tail -N` — там реальная PHP-ошибка/эксепшн.
3. Если ошибки в логе нет (тело ответа пустое, но 500) — это либо PHP
   Fatal/TypeError (не \Exception, не ловится штатным catch) — тогда
   гонять вручную через `docker exec tds-app php -d display_errors=1 -r
   '...'` с прямым вызовом Kernel::run(), либо баг в самом обработчике
   исключений (как было с AdminContext::handleException()).
4. Найдя причину — сверяться с `BUG_PATTERNS.md`: скорее всего это один
   из уже каталогизированных 12+ классов багов декомпиляции, а не новый
   уникальный случай. Правки все примерно однотипные и быстрые.
5. После правки — ОБЯЗАТЕЛЬНО `docker run --rm -v "$(pwd):/app" -w /app
   php:7.4-cli php -l файл.php` (линт) перед тем как считать готовым.
6. Файлы правятся напрямую (`sed -i` или Python-скрипт с `open()/write()`)
   через относительные пути — НЕ через Edit-инструмент (см. пункт 0).

## 5. Что НЕ доделано / что может всплыть дальше

- Пользователь ещё не прошёл ВЕСЬ функционал панели вживую — вероятно,
  всплывут ещё единичные баги того же типа (self:: vs static::/parent::,
  голые константы, "задвоенные параметры", перепутанные if/else). Чинить
  тем же способом.
- Остаётся ~21-23 неподтверждённых кандидата на баг self::-рекурсии
  (первый скан сессии, не все проверены вручную) и ~30 файлов с ещё не
  зачищенными "голыми константами" (пока безобидны, WARNING а не ERROR,
  но при случае лучше добить).
- Нерешённые вопросы у пользователя (см. TODO_IMPROVEMENTS.md):
  HideClickDetect.php (чинить/заменить/выключить), собственный сервис
  скриншотов вместо screenshot.tds24.ru (запланировано, не начато).
- `bin/execute_script.php` — потенциальная дыра при развёртывании через
  RoadRunner вместо Apache (не относится к текущему Docker-стенду на
  встроенном PHP-сервере, но важно для БОЕВОГО деплоя) — см. более раннее
  обсуждение, не переисследовано заново.
- Docker-стенд — это ТЕСТОВЫЙ стенд для локальной проверки, не для прода.
  Прод-деплой (реальный сервер) — отдельная тема, не затронута этой
  сессией.
