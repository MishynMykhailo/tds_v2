# Описание проекта — состояние на момент поставки (до внесённых изменений)

Этот файл описывает, что представляет собой проект и как он был устроен
**изначально, до правок**, внесённых в рамках чистки от лицензии/
самообновления/внешних вызовов. Актуальный список того, что именно
изменено — в `TODO_IMPROVEMENTS.md`. Здесь — снимок "как было".

---

## 1. Что это за проект

PHP-приложение класса **TDS (Traffic Distribution System)** — трекер и
система распределения трафика для партнёрского маркетинга: управление
рекламными кампаниями, потоками (streams), офферами, партнёрскими сетями
(affiliate networks), лендингами, статистикой кликов и конверсий, постбэками,
антибот-детектом, гео-таргетингом.

Внешне и по структуре очень похож на коммерческий продукт Keitaro (те же
термины: Streams/Campaigns/Offers/TrafficSources/Postback/BotDetection/
LpToken, версия `9.13.9`, клиентская библиотека `KClient`), но нигде в коде
буквально не встречается слово "Keitaro" — вероятно, ребрендинг или другой,
но архитектурно близкий продукт. Куплен как готовый проект у фрилансера,
который его собрал/адаптировал.

## 2. Технологический стек

- **PHP 7.2–7.4**, собственный минималистичный фреймворк (без Laravel/
  Symfony-каркаса) — свои Router, Kernel, Dispatcher, DI-подобный
  ComponentManager.
- **RoadRunner** (`spiral/roadrunner`) — опциональный высокопроизводительный
  сервер вместо классического PHP-FPM (`server.php` как отдельная точка
  входа, `vendor/bin/rr serve`).
- **MySQL** — основное хранилище (плюс ClickHouse-конфиг присутствует в
  `application/config/clickhouse`, отдельно для аналитики).
- **Redis** — упоминается в конфиге (кэш/сессии).
- Фронтенд админки — собранный (webpack) бандл (`admin/assets/app.js`,
  `login.js`), похоже на Angular/React-приложение.
- Более 250 миграций схемы БД, накопленных с 2016 года.

## 3. Точки входа

- `index.php` — основной UI/редиректор трафика.
- `api.php` — Click API (`ClickApiContext`).
- `gateway.php` — контекст редиректа-шлюза (`GatewayRedirectContext`).
- `cron.php` — вход для фоновых задач (описано ниже).
- `admin/index.php` — админ-панель.
- `server.php` — альтернативный вход при запуске через RoadRunner.

## 4. Как работала система лицензирования (ДО правок)

Ключевые файлы: `Core/Application/{LicenseService,EssentialService,
EssentialPayload,FeatureService}.php`, `Core/Security/ServerFinderService.php`,
`Core/Sentinel/{Single,SingleKey}.php` (небольшая своя JWT-библиотека).

- Лицензионный ключ хранился в `var/license/key.lic` (обычная строка вида
  `XXXX-XXXX-XXXX-XXXX`), закэшированный токен — в `var/license/hash.lic`.
- Раз в ~2 часа (cron-задача `CheckTsTask`) и при периодической проверке в
  `Bootstrap::initLicense()` приложение отправляло запрос на
  `https://license.tds.io/v1/token/v8` (резерв — `https://reserve.license.tds.io`),
  передавая: IP сервера, лицензионный ключ, версию TDS, домен, версию PHP,
  версию ionCube-загрузчика (если есть), анонимный `tracker_id`
  (`md5(SALT)`), количество пользователей.
- Ответ — подписанный JWT-токен (RS512, публичный ключ зашит в
  `EssentialService::X_V8`), из которого доставался `EssentialPayload`:
  edition (trial/basic/pro/business), лимиты пользователей, доступность
  Click API/Admin API, срок действия лицензии.
- `FeatureService` читал этот payload и на его основе включал/выключал
  фичи в приложении (лимиты пользователей, брендинг, доступ к API и т.д.) —
  **но при этом `isBusiness()` уже был захардкожен в `true`, а срок
  действия и лимиты были явно ослаблены** — то есть копия была уже частично
  пропатчена (нулленная) кем-то до нас, ограничения лицензии были обойдены
  локально ещё до наших правок.
- 10 захардкоженных IP-адресов вендора (диапазоны Hetzner) могли достучаться
  до отдельного роута `RefreshLicenseContext`, чтобы удалённо форсировать
  обновление лицензионного токена конкретной установки.
- Гейт в `Cron/CronTaskRunner/CronTaskRunner.php`: если файла
  `var/license/key.lic` не было или он был пустой — **весь cron целиком
  отказывался запускать вообще любые задачи**, не только лицензионную.

## 5. Как работала система самообновления (ДО правок)

Ключевые файлы: `Component/SelfUpdate/TdsUpdater/TdsUpdater.php`,
`Service/SystemUpdaterService.php`, `Controller/SelfUpdatesController.php`,
консольные команды `system:self_update` / `system:check_update`.

- По клику "Обновить" в админке (или через консоль) приложение обращалось к
  `https://tds.io/license/api/getUpdate` за информацией о новой версии,
  затем скачивало архив с `https://tds.io/releases/<версия>/<пакет>.zip`
  (резервный адрес — сырой IP `159.69.13.34`).
- Скачанный архив распаковывался (`ZipArchive`/`PharData`/`tar` через
  `system()`/`exec()`) и **полностью перезаписывал файлы установки**
  (`mirror($tmpPath, $rootPath, ..., ["override" => true])`).
- Триггер был **только ручной** (кнопка в админке или CLI-команда) — ни
  одна из 19 cron-задач самообновление не запускала автоматически.
- Отдельно был диагностический экран "Проверка системы" (`SelfChecker`) —
  не про обновление, а про здоровье инсталляции: применённые миграции,
  права доступа к папкам, наличие GeoDB-файлов, прогрев кэша, рестарт
  RoadRunner. Эта часть не относится к самообновлению и не была затронута
  правками.

## 6. Cron-система (фоновые задачи)

19 зарегистрированных задач (полный список и описание каждой — см. историю
переписки/можно попросить меня пересобрать отдельным файлом). Коротко по
категориям: обработка очереди кликов/конверсий, чистка старых
кликов/сессий/логов/файлов отчётов, проверка доменов и авто-SSL, выполнение
триггеров на стримах, синхронизация с Facebook/AppsFlyer, прогрев/чистка
кэша, скачивание шаблонов лендингов, и сама лицензионная проверка.

Все они блокировались упомянутым выше гейтом по `var/license/key.lic` —
то есть при отсутствии лицензионного ключа **ничего из этого списка не
работало вообще**, включая критичную для отчётов задачу обработки очереди
кликов (`ExecuteDelayedCommand`) и чистку данных (`PruneClicks`).

## 7. Курсы валют

`Core/Currency/DataSource/ExratesTds.php` — при необходимости конвертации
между валютами (например, оффер в USD, отчёт в EUR) приложение обращалось к
`https://exrates.tds.io/latest?base=...&symbols=...`, передавая лицензионный
ключ в заголовке `x-license-key`, и получало курс обмена.

## 8. GeoIP / антибот-базы

Модуль `GeoDb` поддерживал несколько источников:
- **Хостинговые базы вендора** (`GeoDb/Tds/TdsBotDb2.php`, `TdsCarrierDb.php`,
  а также "Lite"-версии Maxmind/IP2Location/Sypex) — качались с `tds.io`
  (например, `tds.io/files/botsdb`, `tds.io/db/GeoLiteCity.dat.gz`,
  `tds.io/geoip/IP2LOCATION-LITE-DB3.BIN.gz`) — то есть даже "бесплатные"
  Lite-версии сторонних баз на самом деле были зеркалированы через
  инфраструктуру вендора, а не качались напрямую у Maxmind/IP2Location.
- **Полные (платные) версии** Maxmind/IP2Location/Sypex/ProIP — качались
  напрямую у соответствующих провайдеров, с собственным токеном/ключом,
  настраиваемым в панели (`SETTING_KEY`).
- Обновление баз происходило **только вручную** — кнопкой в настройках
  GeoDB или запуском диагностики "Проверка системы"; никакой cron-задачи на
  автоматическое обновление баз не было.

## 9. Прочие сторонние интеграции (не относятся к вендору tds.io напрямую)

- `avscan.ru`, `viruscheckmate.com` — проверка лендингов/доменов на
  антивирусные блэклисты (платные сервисы, опционально включаются ключом в
  настройках).
- `screenshot.tds24.ru` — генерация скриншота-превью локального
  лендинга/оффера при создании/редактировании (автоматически, не
  опционально), с передачей лицензионного ключа в заголовке.
- `api.hideapi.xyz` — фильтр стрима "детект скрытия клика"
  (распознавание визитов через анонимайзер/hide-сервис — техника защиты
  от модераторов рекламных площадок). Логика уже была нерабочей на момент
  получения проекта (артефакты декомпиляции).
- `graph.facebook.com`, `hq.appsflyer.com` — постбэки конверсий/синхронизация
  расходов в собственные рекламные аккаунты пользователя (опционально).
- `api.qrserver.com`, `mxtoolbox.com` — вспомогательные ссылки/виджеты в
  самой админ-панели (QR-код ссылки на кампанию, ручная ссылка проверки
  домена).

## 10. Обнаруженные проблемы/баги в поставленном коде (не связаны с нашими
правками, существовали изначально)

- **Минимум 32 файла** во всём проекте объявлены как `final class
  FooInterface { public abstract function ...; }` вместо корректного
  `interface FooInterface { public function ...; }` — гарантированно
  фатальная ошибка PHP при загрузке класса. Похоже на артефакт инструмента
  декомпиляции/деобфускации исходного ionCube-кода. Полный список — в
  `TODO_IMPROVEMENTS.md`.
- `HideClickDetect.php` — фильтр antи-детекта клоакинга был по факту
  нерабочим (обрыв логики через `exit` вместо реальной отправки запроса).
- `EssentialService::checkLicenseKey()` изначально требовал 2 обязательных
  аргумента, при этом вызывался с одним — потенциальная ошибка аргументов.
- Поставленный `docker-compose.yml`/`Dockerfile` не были рабочими "из
  коробки": отсутствовал `composer.json` (нужен для шага `composer
  install`), отсутствовал `.rr.yaml` (конфиг RoadRunner), отсутствовал
  `vendor/bin/rr` (установщик бинарника RoadRunner), а переменные окружения
  БД в `docker-compose.yml` не совпадали с реально используемым файлом
  `application/config/config.ini.php`.
