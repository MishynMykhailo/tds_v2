# HAND_FIX — что нужно сделать руками (не через код)

Этот файл — инструкция по вещам, которые нельзя починить правкой PHP-кода:
внешние бинарные базы данных, которые нужно скачать и положить в файловую
систему вручную. Остальная документация по этой сессии (баги, история,
план доработок, описание проекта) — в `docs/`.

---

## GeoDB-базы

Приложение поддерживает несколько внешних баз для гео/бот/оператор-детекта.
Автоскачивание с серверов вендора (`tds.io`) отключено намеренно (см.
`docs/TODO_IMPROVEMENTS.md`) — каждую базу нужно положить руками по точному
пути. Если файла нет — соответствующий детект просто не даёт данные,
ничего не падает (кроме шумных ERROR/WARNING в логе).

### ✅ ip2location_lite — сделано, работает

- **Что это:** страна/регион/город по IP.
- **Откуда брать:** официальный бесплатный сайт IP2Location —
  https://lite.ip2location.com/ (нужна бесплатная регистрация).
- **Какую базу качать:** **LITE DB3** — "Country • Region • City".
  Не DB1 (только страна, недостаточно), не DB5/DB11 (лишние поля
  широта/долгота/индекс/часовой пояс — адаптер их не читает, и главное
  файл будет называться иначе).
- **Формат:** **BIN** (не CSV, не CIDR — адаптер использует официальную
  библиотеку `IP2Location\Database`, она читает только `.BIN`).
- **IPv4 или IPv6:** берите **IPv4**-вариант архива (без "IPV6" в имени).
- **Куда класть** (точное имя файла обязательно):
  ```
  var/geoip/IP2Location/lite/IP2LOCATION-LITE-DB3.BIN
  ```
- **Как проверить, что подхватилось:**
  ```bash
  docker exec tds-app php -r '
  require "/app/vendor/autoload.php";
  define("ROOT", "/app");
  \Core\Application\Bootstrap::initClickContext();
  $geoDb = new \Component\GeoDb\Ip2Location\Ip2LocationDb3Lite();
  var_dump($geoDb->exists());
  var_export($geoDb->info("8.8.8.8"));
  '
  ```
  Должно вернуть `bool(true)` и массив с `country`/`region`/`city`.

### ⏳ tds_bot_db2 — не сделано, нужен вендорский файл

- **Что это:** база сигнатур ботов (детект `bot_type`).
- **Куда класть:** `var/bots/botsV2.dat`.
- **Формат:** **проприетарный бинарный формат вендора tds.io**, парсится
  только его собственным адаптером (`TdsBotDb2Adapter.php`). Открытого
  публичного аналога с таким же форматом не существует — нельзя просто
  "скачать откуда-то ещё" и подставить.
- **Реалистичные варианты:**
  1. Получить файл напрямую у вендора (маловероятно с учётом конфликта).
  2. Оставить не заполненным — ничего не сломается, просто этот
     конкретный источник бот-детекта не работает (в приложении есть
     отдельный, независимый список ботов в Settings, не завязанный на
     этот файл).
  3. Написать новый адаптер под независимую базу ботов — отдельная
     задача разработки, не "просто положить файл".

### ⏳ tds_carrier — не сделано, нужен вендорский файл

- **Что это:** база операторов связи / типа соединения (`operator`,
  `connection_type`).
- **Куда класть:** `var/geoip/carriers.dat`.
- **Формат:** тоже проприетарный формат вендора
  (`TdsCarrierDbAdapter.php`), тот же расклад, что и с ботами.
- **Возможная независимая замена в будущем:** MaxMind GeoIP2 ISP
  (платная база, другой формат — потребует новый адаптер, а не просто
  файл). Отдельная задача, если понадобится.

## Общий паттерн для любой новой внешней базы в будущем

1. Найти класс базы в `application/Component/GeoDb/**/*.php` (расширяет
   `AbstractGeoDb`) — там в конструкторе указаны `file_path` (куда класть)
   и `DownloadManager` (если `NullDownloadManager` — значит автоскачивание
   уже отключено намеренно, и файл ждут вручную).
2. Положить файл строго по указанному `file_path` (имя и регистр важны).
3. Проверить через `exists()`/`info($ip)` на живом объекте класса (см.
   пример выше для ip2location_lite) — не через реальный клик, так быстрее
   и не грузит остальной пайплайн.

## Нужно настроить системный cron в Docker dev-стенде (иначе клики/SSL/очереди не работают)

`cron:run` (`bin/cli.php cron:run`) — одноразовая команда, а не демон. Рассчитана на вызов
РЕАЛЬНЫМ системным cron каждую минуту, обязательно от имени `www-data` (сам скрипт отказывается
запускаться под root: "User 'root' can't run this command"). В этом Docker-контейнере (`tds-app`)
никакого системного cron изначально не настроено — из-за этого молча не работает:
- обработка очереди кликов (`ExecuteDelayedCommand` → без этого клики физически не попадают
  в `tds_clicks`, хотя сам трекинг отвечает 200 и выглядит рабочим),
- проверка/продление SSL-сертификатов доменов,
- прочие cron-задачи (prune, self-update check и т.д.).

**Что нужно сделать при следующей настройке контейнера:**
1. Установить `cron`/`supervisor` в `Dockerfile.dev` (сейчас не установлен).
2. Добавить crontab-запись (от `www-data`): `* * * * * cd /app && php bin/cli.php cron:run`.
3. Либо — проще для dev — добавить в entrypoint/supervisor вечный shell-цикл:
   `while true; do su -s /bin/sh www-data -c "cd /app && php bin/cli.php cron:run"; sleep 60; done`.
4. Убедиться, что `/app/cache`, `/app/cache_landing`, `/app/var/**` доступны на запись `www-data`
   (в этой сессии директории оказались `root`-owned 755, т.к. веб-сервер запускается от root, а
   `cron:run` — от `www-data`; временно исправлено через `chmod -R 777`, для постоянного решения
   лучше явно задать одного пользователя для всего или `chown` нужные директории на `www-data`).
5. Проверить `/app/var/bots/` существует (нужна для `PruneUserBotDBCA`) — создать при
   первом запуске, если её нет: `mkdir -p /app/var/bots`.

Без этого шага сессия отладки 2026-08-27 показала: можно почти час гонять живые клики через
curl/Playwright, получать честные HTTP 200 с корректными куками — и НИ ОДИН клик не попадёт в
базу, без единой видимой ошибки в обычном UI/API-тестировании. Проверка "работают ли клики"
всегда должна включать реальный прогон `cron:run` и SELECT из `tds_clicks`, а не только факт
200-го ответа от трекинг-ссылки.

## Обновление: временный крон-луп запущен вручную (2026-08-27, до пересборки Dockerfile)

Пока в `Dockerfile.dev`/entrypoint не добавлен нормальный cron (см. раздел выше), в контейнере
`tds-app` вручную запущен фоновый цикл:
```
while true; do su -s /bin/sh www-data -c "cd /app && php bin/cli.php cron:run" >> /app/var/log/cron_loop.log 2>&1; sleep 15; done
```
Он НЕ переживёт перезапуск контейнера `tds-app` — это просто фоновый процесс внутри текущего
запущенного контейнера. Если контейнер перезапустят/пересоздадут, эту команду нужно будет
выполнить заново (или, что правильнее, довести до конца пункт 1-3 из раздела выше и зашить это
в сам образ/entrypoint, чтобы больше не приходилось помнить об этом руками).
