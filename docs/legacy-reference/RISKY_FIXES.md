# Рискованные фиксы — где я не восстанавливал, а решал сам

Этот файл — отдельно от `docs/FIXES_LOG.md`. Там — все фиксы подряд. Здесь — только те, где
граница между "починил явно сломанное" и "поменял поведение по своему инженерному решению"
размыта. Критерий разделения:

- **Категория A — восстановление семантики.** Код был технически сломан: падал с ошибкой,
  бесконечно зацикливался, содержал переменную, которая нигде не определена, или явно
  противоречил своему же собственному соседнему коду/логам/паттерну в том же классе. Здесь я не
  придумывал новое поведение — просто возвращал код в рабочее состояние, причём почти всегда
  однозначным способом (есть только один разумный вариант "как должно было быть").
- **Категория B — моё решение.** Код был синтаксически рабочим, ничего не падало — но по
  результату явно вело себя не так, как нужно. Я сам решил, как это исправить, опираясь на
  наблюдение/эксперимент, а не на явную техническую поломку в самом коде. Здесь **не факт**, что
  я угадал оригинальный замысел автора — это моя инженерная гипотеза.

Категория A — я в них уверен, это не обсуждается. Категория B — сюда стоит вернуться и
перепроверить руками/на реальном проде, прежде чем полностью доверять.

## Категория B — сделано по моему решению, не факт из кода

### 1. `application/Traffic/Device/Service/RealRemoteIpService.php` — фильтрация REMOTE_ADDR

**Было:**
```php
public function find(\Traffic\Request\ServerRequest $request)
{
    $possibleRealIps = [$this->_ipFromOperaMini($request), $this->_ipFromXRealIp($request),
        $this->_ipFromXForwardedFor($request), $this->_ipFromForwarded($request),
        $this->_ipFromCfConnectingIp($request), $this->_ipFromRemoteAddr($request),
        $this->_lastHope($request)];
    foreach ($possibleRealIps as $ip) {
        if ($this->_isCorrectIpForHeader($ip)) {
            return $ip;
        }
    }
    return $ip;
}
```

**Стало:**
```php
public function find(\Traffic\Request\ServerRequest $request)
{
    $possibleRealIps = [$this->_ipFromOperaMini($request), $this->_ipFromXRealIp($request),
        $this->_ipFromXForwardedFor($request), $this->_ipFromForwarded($request),
        $this->_ipFromCfConnectingIp($request)];
    foreach ($possibleRealIps as $ip) {
        if ($this->_isCorrectIpForHeader($ip)) {
            return $ip;
        }
    }
    $remoteAddr = $this->_ipFromRemoteAddr($request);
    if (!empty($remoteAddr)) {
        return $remoteAddr;
    }
    return $this->_lastHope($request);
}
```

**Почему это B, а не A:** старый код не падал и не содержал явной технической ошибки. Я решил,
что фильтр "выкинуть IP из диапазона 192.168.*/127.0.*" не должен применяться к `REMOTE_ADDR`
(его нельзя подделать, в отличие от заголовков) — это моя логика, не факт из кода.

**Что будет, если откатить:** в нашей Docker dev-среде IP снова будет "0"/`Unknown` для всех
кликов (наблюдаемая проблема). На обычном проде с публичным IP — почти наверняка ничего не
изменится (реальные посетители редко приходят с приватных адресов). Риск отката: минимальный на
типичном проде, критичный для локальной разработки/тестов.

### 2. `application/Traffic/Session/Storage/RedisStorage.php` — TTL≤0 при сохранении сессии уникальности

**Было:**
```php
$oldTTL = \Traffic\Redis\Service\RedisStorageService::instance()->ttl($redisKey);
$ttlInSec = max($oldTTL, $ttlInSec);
\Traffic\Redis\Service\RedisStorageService::instance()->setEx($redisKey, $ttlInSec, $encodedData);
```

**Стало:**
```php
$oldTTL = \Traffic\Redis\Service\RedisStorageService::instance()->ttl($redisKey);
$ttlInSec = max($oldTTL, $ttlInSec);
if ($ttlInSec > 0) {
    \Traffic\Redis\Service\RedisStorageService::instance()->setEx($redisKey, $ttlInSec, $encodedData);
} else {
    \Traffic\Redis\Service\RedisStorageService::instance()->set($redisKey, $encodedData);
}
```

**Почему это B:** старый код не падал (PHP не бросает исключение на `false` от Redis) — просто
Redis молча отказывался сохранять при TTL=0 и данные терялись без единой ошибки в логах. Я сам
решил, что при TTL≤0 нужно сохранять БЕЗ срока жизни, а не пропускать сохранение вовсе — это
осмысленный выбор поведения, не факт из кода.

**Что будет, если откатить:** любая кампания с пустым/нулевым полем "Uniqueness TTL" будет
молча терять данные об уникальности (в точности проблема, которую ты заметил). Реальный,
подтверждённый экспериментом баг именно в этом месте — но само РЕШЕНИЕ (что делать вместо
`setex`) — моё.

### 3. `application/Traffic/Http/Service/HttpService.php` — таймаут для Guzzle-клиента

**Было:**
```php
public function buildDefaultClient()
{
    $client = new \GuzzleHttp\Client();
    $this->setClient($client);
}
```

**Стало:**
```php
public function buildDefaultClient()
{
    $client = new \GuzzleHttp\Client(["connect_timeout" => 10, "timeout" => 20]);
    $this->setClient($client);
}
```

**Почему это B, причём самое "моё" из всех:** это не фикс сломанной логики вообще — это
ДОБАВЛЕНИЕ нового поведения, которого не было в коде вообще ни в каком виде. Я лично словил
зависание `cron:run` навечно при проверке недоступного тестового домена и решил добавить
таймауты как защиту. Конкретные цифры (10 и 20 секунд) — тоже мои, взяты "на глаз", не из кода
и не из документации проекта.

**Что будет, если откатить:** любой недоступный/медленный внешний домен (проверка SSL, постбек,
Pull-API партнёрской сети) может подвесить весь cron навсегда, без таймаута и без ошибки в
логах — ровно то, что уже один раз произошло в этой сессии. Стоит держать этот фикс, но цифры
таймаутов — можно спокойно менять под реальные нужды, я их не откуда-то списал.

### 4. `application/Component/Users/Model/AclRule.php` — строгое сравнение вместо нестрогого (найдено параллельным QA-агентом, не мной лично, но попадает в ту же категорию)

**Было:** `in_array($groupId, $this->getGroups())` — нестрогое сравнение.
**Стало:** `in_array((string) $groupId, $this->getGroups(), true)` — строгое сравнение.

**Почему это B:** нестрогий код не падал. Проблема была в том, что `"0" == 0` истинно в PHP, а
пустой выбор ACL сохраняется как `["0"]` (сентинел-заглушка), из-за чего пользователь с
"ничего не выбрано" видел вообще все сущности без группы (`group_id = 0`). Решение "сделать
сравнение строгим" — инженерный вывод из данных, не факт из кода.

**Что будет, если откатить:** вернётся дыра в безопасности — пользователь с ACL
"доступ только к выбранным сущностям" и пустым списком увидит вообще все негруппированные
кампании/офферы/лендинги. **Этот однозначно НЕ стоит откатывать**, несмотря на то что формально
это категория B — здесь цена ошибки (безопасность) перевешивает неопределённость происхождения.

## Категория A — для сравнения, что считается "не обсуждается" (примеры из этой же сессии)

- `GetCampaign::fallback() {}` — пустой метод там, где у ВСЕХ соседних классов (`GetStream`,
  `GetResource`) на этом месте реальный код чтения из БД. Один правильный вариант, скопирован
  один в один с соседей.
- `ResolveClickDevice::process($entries)` — тело метода читало переменную `$data`, которая
  нигде не объявлена (только `$entries`-параметр). Без `foreach` по `$entries` метод в принципе
  не мог работать. Однозначный фикс.
- `FilterAttributes`/`HttpService`/`DomainCheckerService` — потерянные `use(...)` у замыканий:
  без них замыкание видит `NULL` вместо реальной переменной снаружи. Один способ починить.
- `CronService::getLastRun()` — вызывал `$task->get("executed_at")` напрямую, хотя в ТОМ ЖЕ
  классе `CronTaskStatus` уже есть готовый геттер `getExecutedAt()`, который правильно кастует
  строку в `DateTime`. Просто не тот метод вызвали.
- `AbstractModel::getFields()` — не откатывал fallback на `_realColumns()`, хотя в ТОМ ЖЕ
  файле, в методе `definition()`, уже используется точно такой же паттерн
  (`static::$_fields ?: static::_realColumns()`). Я просто повторил уже существующий в классе
  приём.

Здесь риска почти нет — сам код показывает, что "правильный" вариант один, я не гадал.
