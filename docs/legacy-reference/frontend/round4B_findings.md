## Найденные и исправленные баги

### 1-5. Пять багов в подсистеме DBCA (Additional Bot IPs) — `?object=botlist.addBotList` падал 500

Живой тест: Settings → Bots → "Additional Bot IPs" → Add → ввёл `8.8.8.8` + `9.9.9.0/24` →
Save → **500 Internal Server Error**. В логе:
`main.ERROR: in /app/application/Core/TdsDb/DBCA/DbWriter.php line 58: Allowed memory size
of 134217728 bytes exhausted`. Раскопал полную цепочку из 5 багов в самописном бинарном
хранилище "DBCA" (`application/Core/TdsDb/DBCA/*`, `application/Core/TdsDb/Common/IpSegment.php`,
`application/Component/GeoDb/Tds/DbcaClient.php`, `application/Component/BotDetection/Service/UserBotsService.php`)
— используется для хранения списка бот-IP (и потенциально любых будущих "TdsDb"-баз того же
формата). Показательный случай, когда один симптом (500 при сохранении) скрывал 5
независимых багов подряд — каждый следующий проявлялся только после фикса предыдущего.

1. **`application/Core/TdsDb/Common/IpSegment.php`** — `setIp($inVal, $mVal)` принимал
   `$mVal` **по значению**, а не по ссылке, и присваивал `$mVal = ...` — то есть локальный
   параметр менялся, но `$this->startIp`/`$this->endIp` (реальные свойства объекта) **никогда
   не устанавливались**. `setStartIp()`/`setEndIp()` вызывают `$this->setIp($startIp,
   $this->startIp)` — по всей видимости, `$mVal` должен был быть параметром по ссылке (`&$mVal`),
   чтобы присваивание внутри `setIp()` реально долетало до свойства объекта через reference.
   Без этого КАЖДЫЙ `IpSegment` в проекте имел `startIp`/`endIp` = `NULL` навсегда — вся
   логика пересечения диапазонов IP (`checkIntersection()`) работала на мусорных данных.
   Проверено: `new IpSegment(ip2long("8.8.8.8"), ip2long("8.8.8.8"))->getStartIpFloat()`
   возвращал `NULL` до фикса, `134744072` после. Исправлено: `setIp($inVal, &$mVal)`.

2. **`application/Core/TdsDb/DBCA/DbWriter.php`, `writeContent()`** — классический
   декомпиляционный баг "do-while с resetData() внутри тела + инвертированное условие
   выхода":
   ```php
   do {
       $data = $this->dbData->resetData();      // сбрасывает указатель на ПЕРВЫЙ элемент
       ...                                        // КАЖДУЮ итерацию!
       $this->writeVarChar($data[...CODE_POS]);
   } while (!($data = $this->dbData->getNext())); // выходит, когда getNext() успешен (наоборот)
   ```
   Из-за `resetData()` внутри тела цикл никогда реально не продвигается по данным — на
   практике записывается **только первый элемент** (или уходит в бесконечный цикл, если
   элемент всего один — `getNext()` на единственном элементе всегда `false`, `!false=true` →
   цикл длится вечно). При этом заголовок файла (`writeHeader()`) честно пишет реальное
   количество элементов (`getCount()`), из-за чего дальше при чтении файла количество
   "объявленных" элементов не совпадает с реально записанными — читатель уходит читать за
   пределы контента, попадая в область хеш-индекса и интерпретируя её как испорченный
   varchar. Исправлено на нормальный цикл:
   `$data = resetData(); while ($data !== false) { ...; $data = getNext(); }`.

3. **`application/Core/TdsDb/DBCA/DbWriter.php`, `writeHashIndex()`** — внутренний
   `while ($ipSeg->checkIntersection($ipSeg2))` не имел выхода на случай, когда данные
   кончились (`$curData === false`): `$ipSeg` в этом случае просто не обновлялся (оставался
   равен последнему реальному сегменту) и продолжал "пересекаться" с текущей хеш-корзиной
   бесконечно → `$hashList[]` рос без остановки → тот самый `Allowed memory size exhausted`
   на строке 58 (`$hashList[] = ...`). Плюс `$i++` в конце внешнего цикла было условным
   (`if ($curData !== false) { $i++; }`), из-за чего при исчерпании данных внешний цикл
   тоже никогда не продвигался. Исправлено: добавлено условие `$curData !== false` во
   внешнюю часть `while`, `$i++` сделан безусловным (нужен для дозаписи оставшихся пустых
   хеш-корзин после исчерпания данных).

4. **`application/Core/TdsDb/DBCA/DbReader.php`, `getNextHashListPtrs()`** — классический
   Паттерн 8 (инвертированное условие цикла + инвертированное условие внутри):
   ```php
   while (count($this->hashPtrDeclared) <= $this->curHashPos) { // должно быть >, а не <=
       ...
       if ($this->curHashListCount == 0) {   // должно быть != 0
           return true;
       }
   }
   return false;
   ```
   Как написано, цикл вообще не выполнялся с самого начала (`count > 0 <= 0` всегда false
   при первом вызове), поэтому `getFullList()`/`checkConsistency()` не читали НИ ОДНОЙ
   хеш-корзины — `getFullList()` (используется для показа списка в модалке "Edit" на
   Settings → Bots) возвращал бы пустой массив. Плюс сама логика "нашли непустую корзину"
   была перевёрнута (возврат `true` на ПУСТОЙ корзине, а не на непустой). Исправлено на
   `while ($this->curHashPos < count(...))` и `if ($this->curHashListCount != 0) { return
   true; }`.

5. **`application/Component/GeoDb/Tds/DbcaClient.php`, `rawInfo()`** — реальный
   production-путь поиска бота по IP (используется в клик-пайплайне через
   `TdsBotDb2Adapter`/`InternalUserBotDb`, независимая от `DbReader` быстрая
   hash-based реализация). Бесконечный цикл:
   ```php
   while ($i < $listCount) {
       ...
       if ($curSegmentMin <= $ipFloat && $ipFloat <= $curSegmentMax) {
           $codePtrs = ...;
           $found = true;      // $i НЕ инкрементируется в этой ветке!
       } else {
           $i++;
       }
   }
   ```
   При совпадении IP с сегментом (`$found = true`) `$i` никогда не увеличивался — вечный
   цикл на каждый успешный лукап бота по IP. Учитывая, что это код **клик-пайплайна**
   (проверка "является ли IP ботом" на каждом клике), при живом трафике с включённым
   `check_bot_ip` и непустым списком бот-IP это привело бы к зависанию/500 на КАЖДОМ клике
   с IP из списка. Исправлено: `break;` сразу после нахождения (семантически корректно —
   диапазоны не пересекаются, дальше искать нечего).

Проверено полным round-trip тестом напрямую через PHP (запись реального `.dbca` файла с
2 диапазонами → чтение через `DbReader::getFullList()` + `checkConsistency()` → чтение через
`DbcaClient::rawInfo()` для найденного/ненайденного IP) — всё сошлось идеально после всех
5 фиксов. Затем подтверждено вживую через Playwright: Settings → Bots → Add
(`8.8.8.8` + `9.9.9.0/24`) → count=2, без 500; Edit показывает `8.8.8.8\n9.9.9.0-9.9.9.255`;
Remove (`8.8.8.8`) → count=1 (см. баг №6 ниже); Clean → count=0 (кнопка требует подтверждения
через кастомную Angular-модалку "Clear IP list? Yes/Cancel", а не нативный `confirm()` —
не баг, просто особенность UI, важно для написания тестов).

### 6. `application/Component/BotDetection/Service/UserBotsService.php` — `_cropRanges()` терял несвязанные записи при удалении (потеря данных!)

Живой тест: список содержал `8.8.8.8` + `9.9.9.0/24` (2 записи), затем через "Remove"
удалил только `8.8.8.8` — итоговый список должен был остаться с одной записью
(`9.9.9.0/24`), но реально **весь список обнулился** (count 2 → 0), хотя `9.9.9.0/24` вообще
не пересекается с удаляемым диапазоном.

Причина — отсутствующий `return` в конце функции:
```php
private function _cropRanges($src, $excludeList)
{
    $result = [];
    ...
    foreach ($excludeList as $excludeRange) {
        ...
        if ($sourceMax < $sourceMin) {
            if ($sourceMin <= $sourceMax) {   // недостижимо (условие уже false выше)
                $result[] = [...];
            }
            return $result;
        }
    }
    // <-- НЕТ return здесь! Если ни один excludeRange не тронул диапазон,
    //     функция проваливается в конец и возвращает NULL
}
```
Если запись из старого списка вообще не пересекается ни с одним диапазоном исключения (как
`9.9.9.0/24` не пересекается с `8.8.8.8`), `foreach` доходит до конца без единого `return`,
и функция **неявно возвращает `NULL`**. Вызывающий код (`excludeFromList()`) делает
`foreach ($newItems as $newItem)` по этому `NULL` — PHP просто ничего не добавляет в
результат (тихий `Invalid argument supplied for foreach()` без падения) — запись **исчезает
из финального списка**, хотя её не просили удалять. Это баг потери данных: любая
операция "Remove" на список из 2+ непересекающихся диапазонов **стирала все диапазоны,
кроме тех, что физически пересекались с удаляемым** — то есть при удалении ОДНОГО IP из
списка терялись ВСЕ остальные, не связанные с ним записи.

Исправлено: добавлен безусловный `return $result;` в конец функции, с довеском
`if ($sourceMin <= $sourceMax) { $result[] = [$sourceMin, $sourceMax, ""]; }` перед ним —
чтобы неизменённый (или частично обрезанный, но не полностью съеденный) диапазон тоже
попадал в результат. Заодно убрана мёртвая/недостижимая внутренняя проверка
`if ($sourceMin <= $sourceMax)` внутри веток раннего `return` (там `$sourceMax < $sourceMin`
уже гарантировано условием снаружи — второй `if` физически никогда не может быть true).

Проверено вживую Playwright: список `8.8.8.8` + `9.9.9.0/24` → Remove `8.8.8.8` → count=1,
Edit показывает оставшийся `9.9.9.0-9.9.9.255` (было: count=0, список полностью обнулялся).

## Инфраструктурная находка (не баг кода, но важно)

Во время тестирования контейнер `tds-mysql` внезапно упал (`Exited (137)` — SIGKILL, похоже
на OOM killer хоста; в его логе "Database was not shutdown normally" при рестарте). Скорее

`Allowed memory size of 134217728 bytes exhausted` (баг №3 выше) — сам PHP CLI-процесс
корректно упал по своему memory_limit (128MB), не должен был задеть MySQL, но общая память
хоста могла быть на пределе. Перезапущено (`docker start tds-mysql`), проверена целостность
данных — восстановился штатно (InnoDB crash recovery, redo log applied), данные не
повреждены. **Для координатора**: если параллельный агент (round4A) видел в это время
провалы запросов к БД — это была временная (~2 минуты) недоступность MySQL, уже
устранена, не связана с багами кода.

  `redis_server` — в UI как отдельное поле НЕ отображается на этой инсталляции (нет
