# Архитектура пересборки фронтенда: синтез + план

Этот документ — свод результатов двух параллельных исследований:
- `docs/frontend/backend_api_reference.md` — что реально отдаёт/ждёт бэкенд;
- `docs/frontend/frontend_analysis.md` — что реально вызывает и рендерит текущий Angular-бандл.

Здесь — (1) сопоставление найденных расхождений между "фронт думает X" и "бэкенд делает Y",
(2) список критичных "гочей" контракта, которые нельзя терять при пересборке, (3) собственно
предложение архитектуры dev-сборки вместо текущего непрозрачного webpack-бандла.

См. отдельный файл `docs/frontend/questions_for_new_proj.md` — чек-лист вопросов и вещей, которые нужно проверить/решить ДО начала переписывания фронтенда (что уточнить вживую в реальной админке, контрактные "гочи", архитектурные решения по выбору итогового стека, технические предпосылки).

## 1. Расхождения фронт↔бэкенд, требующие ручной проверки

### 1.1 Схема стрима — ✅ РЕШЕНО (проверено вживую, Playwright, 2026-08-27)

Ровно 3 варианта, без 4-го: `landings` ("Landing pages & offers" — показывает ОБА пикера,
Landing Pages и Offers, одновременно, подтверждено скриншотом), `redirect` ("Direct URL" —
Redirect Type + URL), `action` ("Action" — один select с действием, напр. "404 NotFound").
Расхождение с независимым чтением кода frontend-агентом закрыто — тот код, вероятно, относился
к внутренней структуре React-компонента, а не к количеству реально показываемых пользователю
вариантов.

### 1.2 `streams.export` — фронт не нашёл вызов, бэкенд endpoint есть

Backend-агент подтвердил: `StreamsController::exportAction` существует, принимает `campaign_id`
(POST), возвращает `{"url": "..."}`. Frontend-агент не смог найти конкретное место вызова в
минифицированном коде (см. п.5.1 `frontend_analysis.md`), но подтвердил, что в модалке экспорта
стримов кампании вызывается `Stream.export(...)`. **Вывод: расхождения на самом деле нет** —
endpoint существует, это просто пробел в ручной трассировке минифицированного кода. При
пересборке просто реализовать вызов `POST ?object=streams.export`, как задокументировано в
backend-справочнике §10.2.

### 1.3 Симуляция клика — ✅ РЕШЕНО (найдено в коде фронтенда, 2026-08-27)

Гипотеза backend-агента была неверной: специального admin-эндпоинта симуляции действительно нет,
но это не потому что фича не реализована, а потому что она **вообще не идёт через admin API**.
"Simulate traffic" — пункт меню Maintenance (не кнопка в форме кампании) и пункт контекстного меню
строки грида кампаний → `simulationService.open()`. Реализация (`components.simulation.services`,
app.js ~112871-112996):

- Строит "случайные характеристики" клика (гео/устройство/etc, вытянутые из пулов параметров
  трафик-сорса кампании через `getRandomCharacteristics()`);
- Делает СЕРИЮ настоящих `POST` запросов на `<root>/api.php` — это **публичный Click API**
  (`Traffic\Context\ClickApiContext`, см. §1 `backend_api_reference.md`), НЕ `?object=...`;
- Каждый запрос — с флагами `token:<campaign_token>, charset:"utf-8",
  save_to_stats:<bool из формы>, log:true, version:2, always_empty_cookies:true`;
- `log:true` заставляет Click API вернуть подробный лог обработки клика в ответе
  (`response.data.log`), который стримится построчно в `.simulation-output` — живая консоль в
  модалке;
- Прогоняется **реальный** клик-пайплайн (не dry-run), просто с `always_empty_cookies` и
  опционально без записи в статистику (`save_to_stats:false`);
- Доступно только Trial/Pro и выше (`licenseService.isTrialEdition()||isProAndHigher()`), иначе
  `showProError()`.

**Для пересборки:** переиспользовать существующий публичный Click API (`api.php`) с этими же
флагами — отдельный "dry-run" эндпоинт заводить не нужно, это не требуется и в оригинале.
`docs/frontend/backend_api_reference.md` §11 нужно поправить — там ошибочно написано, что
функциональность не найдена/не реализована.

### 1.4 `Stream.favourites` / `Stream.perform` — не сопоставлены с конкретными backend-экшенами

Frontend-агент увидел в Angular-ресурсе `Stream` действия `favourites` и `perform`, которых нет в
списке экшенов `StreamsController`, задокументированном backend-агентом. Вероятные объяснения:
`favourites` — это на самом деле отдельный ресурс `FavouriteStreams` (`?object=favouriteStreams`,
подтверждён backend-агентом отдельно, §10.2), просто в Angular он замаплен как метод общего
`Stream`-сервиса, а не отдельного `$resource`. `perform` — не идентифицирован ни с одной стороны;
может быть легаси/неиспользуемый код. **Проверить руками** через Network-таб при клике на
"избранное" у стрима и поиском живых вызовов `perform` (возможно, тестовый прогон одного стрима —
не пайплайна целиком).

### 1.5 `labels.index` — подозрение на баг возврата не того типа

Backend-агент нашёл: `LabelsController::index` приводит результат `labelsFor()` к `(int)`, хотя по
семантике (судя по имени и по использованию `Label`-ресурса на фронте — `query`/index для списка
меток) должен возвращать список. Это похоже на ещё один хвост декомпиляции (см. паттерны в
`docs/BUG_PATTERNS.md`) — вне scope текущего фронтенд-исследования, но стоит завести как
отдельный пункт в `docs/BUG_PATTERNS.md`/`docs/TODO_IMPROVEMENTS.md` для ручной проверки в живой
системе (клик по меткам в UI + просмотр реального ответа/лога).

## 2. Критичные "гочи" контракта — нельзя потерять при пересборке

Собрано из обоих документов — конкретные детали, которые выглядят как "странности", но являются
осознанным (или зацементированным легаси) поведением, которое новый фронтенд/бэкенд обязаны
воспроизвести один-в-один, иначе тихо сломается сохранение/чтение данных:

1. **`ingore_prefetch`** (Settings → Main) — опечатка в имени поля намеренно не исправляется,
   зашита и в бэкенде, и во фронтенде.
2. **Инвертированная семантика** `cookies_enabled` (`"0"`=да, `"1"`=нет) и `disable_stats`
   (`0`=собирать статистику, `1`=не собирать) — имя поля не соответствует "интуитивному" смыслу.
3. **JSON-в-поле** — `stream_filters.payload`, `streams/offers/landings.action_options`,
   `acl_resources.resources`, `campaigns.parameters` — все хранятся в БД как JSON-строка и
   обязаны проходить через геттер модели (`getPayload()`/`getActionOptions()`/`getResources()`/
   `getParameters()`), а не читаться напрямую полем — уже было источником критичных багов
   декомпиляции (см. `docs/FIXES_LOG.md`).
4. **Контракт серверной валидации форм**: бэкенд обязан отвечать HTTP 406 с телом
   `{ "имя_поля": ["текст ошибки", ...] }`; фронтенд ищет DOM-элемент
   `[field-name="имя_поля"]`. Любое другое имя поля в ответе либо переименование поля без
   синхронизации — ошибка тихо улетает в общий toast без привязки к конкретному инпуту.
5. **Батч-конверт** (`?batch`/`?bulk`) всегда возвращает HTTP 200 на верхнем уровне; реальный
   статус каждого под-запроса — внутри `statusCode` элемента массива ответа.
6. **Формат ошибок не единый**: JSON почти везде, кроме "прочих" необработанных исключений
   (`CommonErrorHandler`) — там `text/html`. REST AdminApi (`/admin_api/vN`) заворачивает вообще
   любую ошибку (кроме лицензионной) в HTTP 402.
7. **`id`/`ids` взаимозаменяемы** почти во всех массовых операциях (`archive`/`restore`/`clone`/
   `enable`/`disable`) — одиночный `id` молча превращается в `ids=[id]`.
8. **"Мягкое" удаление = архивирование**, физическое удаление — только через отдельный
   `cleanArchive` (обычно требует тех же прав, что и создание).
9. **Content-Type тела запроса не учитывается** — тип определяется по первому символу тела
   (`{`/`[` → JSON, наличие `&` → urlencoded). Можно слать голый JSON без корректного заголовка.
10. **Кука `states` не httpOnly** — читаема из JS; это осознанное (хоть и небезопасное) поведение
    оригинала, стоит явно решить при пересборке, воспроизводить ли один-в-один или чинить.

## 4. Ключевая архитектурная развилка: React внутри Angular

Важнейший факт из frontend-анализа: React — не изолированный виджет, а **второй UI-слой**,
рендерящий тело всех гридов (`gridReact`), все react-select-дропдауны, весь виджет управления
стримами кампании, экран Editor (с Ace) и экран Integrations. Мост — `react2angular`,
пробрасывающий даже Angular `$injector` внутрь React-дерева (виджет `streams`).

Это осознанное дизайн-решение оригинальной команды (вероятно, чтобы получить производительный
виртуализированный рендеринг гридов и богатые компоненты типа react-select, не переписывая всё
приложение на React). Для новой dev-сборки нужно явно выбрать один из двух путей:

**Вариант A — сохранить гибридную архитектуру Angular+React.**
Плюсы: минимальный риск регрессий, повторяем ровно то же поведение, что сейчас (UX уже
отработан на реальных пользователях), можно постепенно переносить экраны без переписывания
React-частей заново.
Минусы: две UI-парадигмы одновременно усложняют поддержку и онбординг нового разработчика,
`react2angular`-мост — дополнительный слой абстракции, который тоже придётся поддерживать.

**Вариант B — полностью отказаться от React, переписать grid/react-select-виджеты на чистом
Angular (или заменить на готовые Angular-нативные компоненты, например `ui-grid`/`ag-grid` +
`ui-select`).**
Плюсы: один технологический стек, проще поддерживать в долгосрочной перспективе — именно то,
о чём беспокоится задача ("проблематично поддерживать").
Минусы: экран Streams-виджета и грид — самые сложные и самые часто используемые части всей
админки; переписывание "с нуля" рискует внести регрессии именно в самое критичное место, и
объём работы существенно больше, чем при варианте A.

**Рекомендация:** начать с Варианта A (сохранить React-мост как есть) для быстрого выхода на
рабочую dev-сборку с минимальным риском, и рассмотреть постепенную миграцию отдельных
React-виджетов на Angular-нативные аналоги позже, по одному экрану за раз, только если конкретно
этот виджет станет узким местом поддержки. Не переписывать всё сразу.

## 5. Предлагаемая dev-архитектура (вместо непрозрачного webpack-бандла)

Цель — не "восстановить оригинальный исходный код 1-в-1" (это физически невозможно без
sourcemap/конфига сборки, см. более раннее исследование в этой сессии с `webcrack`), а
**написать новый, читаемый, поддерживаемый фронтенд-проект, поведенчески совместимый с текущим
бэкендом** — то есть renderить те же экраны, дёргать те же `?object=` эндпоинты с теми же
полями, но с нормальной структурой файлов и вменяемой сборкой.

### 5.1 Структура проекта (предложение)

```
frontend/
  package.json
  webpack.config.js (или vite.config.js — см. ниже)
  src/
    app.module.js                  # корневой Angular-модуль, DI-сборка всех фич-модулей
    core/
      http/                        # обёртка над $http (аналог текущего Gg.a), batch-режим (§2.4)
      auth/                        # states-cookie логин/логаут, guard роутов
      grid/                        # общая Grid-инфраструктура (React-мост, см. §4 Вариант A)
      formly/                      # кастомные типы (vInput/vSelect/vUiSelect/...), wrappers
      i18n/                        # i18next + react-i18next обвязка
    features/
      campaigns/
      streams/                     # включая React-виджет управления стримами
      offers/
      landings/
      editor/                      # React + Ace
      traffic-sources/
      domains/
      users-acl/
      geo-db/
      reports/
      conversions-clicks/
      settings/
      migrations/
      dashboard/
      integrations/
      affiliate-networks/
      logs/
    shared/
      services/                    # slugGeneratorService, clipboard, notificationService, ...
      components/                  # переиспользуемые UI-виджеты вне Grid/Formly
  docs/ → ссылки на docs/frontend/backend_api_reference.md как источник правды по контракту
```

Каждая `features/<name>` папка — по образцу текущих Angular-модулей, задокументированных в
`frontend_analysis.md` (раздел 3): свой `*.module.js`, `*-form.service.js` (formly-конфиг полей),
`*.resource.js` (обёртка над `?object=` вызовами, 1-в-1 по документированному в
`backend_api_reference.md` контракту), `*.component.js`.

### 5.2 Сборка: webpack5 (ближе к оригиналу) или Vite

Оригинал собран webpack'ом (webpack-модули видны в бандле). Для dev-сборки два разумных пути:

- **webpack5 + babel** — минимальный риск несовместимости со старыми Angular 1.x-паттернами
  (глобальные `angular.module(...)` side-effect импорты, `require()`-стиль legacy-библиотек типа
  jQuery UI/Snap.js, которые не всегда дружат с ES-модулями "из коробки").
- **Vite** — быстрее в dev-режиме (HMR), но местами капризнее с legacy CommonJS/globals-стилем
  библиотек (jQuery-плагины, `angular.module` side-effects) — потребует явных `optimizeDeps`/
  `resolve.alias` настроек под каждую проблемную зависимость.

**Рекомендация:** начать с webpack5 (меньше сюрпризов с легаси-стеком), рассмотреть переход на
Vite отдельным шагом позже, когда/если весь легаси-код (jQuery/Snap.js/ace) будет либо заменён,
либо явно обёрнут в совместимые адаптеры.

### 5.3 Дев-прокси к бэкенду

Бэкенд уже поднят в Docker (`tds-app`, `tds-mysql`, `tds-redis` — см. `docs/SESSION_HANDOFF.md`).
Dev-сервер фронтенда должен проксировать `?object=...`/`/admin_api/...` запросы на
`http://localhost:8090` (текущий проброшенный порт `tds-app`), сохраняя куку `states` (см. §2 п.10
— она не httpOnly, так что и обычный XHR из dev-сервера на другом порту будет работать, если
настроить `withCredentials`/CORS на бэкенде для dev-origin, либо проксировать через тот же origin
через `devServer.proxy`, что проще и безопаснее).

## 6. Предлагаемый порядок работ (по фазам, от простого к сложному)

1. **Фаза 0 — Скелет.** Пустой Angular-модуль + ui-router + auth (логин через кука `states`,
   §2 backend-справочника) + dev-прокси к Docker-бэкенду. Критерий готовности: залогиниться и
   увидеть пустой Dashboard.
2. **Фаза 1 — Простые CRUD-экраны без React.** Domains, TrafficSources, Migrations, GeoDb,
   Settings (4 вкладки) — здесь нет React-гридов (кроме списков, которые пока можно временно
   рендерить нативной Angular-таблицей без виртуализации), зато полностью проверяется связка
   Formly + сервер-валидация (406 + `field-name`, см. §2 п.4) и все задокументированные "гочи"
   контракта (§2).
3. **Фаза 2 — Grid-инфраструктура.** Реализовать общий `Grid`-сервис + принять решение по §4
   (сохранить React-мост для тела грида или писать нативно). Это блокирует все последующие
   списочные экраны, поэтому делается отдельной фазой до них.
4. **Фаза 3 — Основные сущности с формами.** Campaigns, Offers, Landings, AffiliateNetworks —
   используют Grid (фаза 2) + Formly (фаза 1) + LocalFile-аплоад архивов (Offers/Landings).
5. **Фаза 4 — Streams-виджет.** Самая сложная часть (React-виджет с `$injector`, схема
   action/redirect/landings — см. п.1.1, разобраться руками в реальной админке ДО реализации),
   плюс StreamFilters/Triggers.
6. **Фаза 5 — Editor (Ace) и Integrations.** React-экраны, отдельная интеграция Ace Editor.
7. **Фаза 6 — Reports/Dashboard/Clicks/Conversions.** Chart.js, daterangepicker, экспорт CSV/HTML.
8. **Фаза 7 — Users/ACL/Profile/ApiKeys, Logs, Labels, Search.** Оставшиеся административные
   экраны.
9. **Фаза 8 — Login/License отдельные бандлы.** Простые самостоятельные страницы, низкий
   приоритет, можно вообще оставить как есть (текущий `login.js`/`license.js`) до последнего.

Каждую фазу — сверять по двум документам (`backend_api_reference.md` как контракт "что
отправлять/что придёт", `frontend_analysis.md` как справочник "что реально было в UI") и вручную
кликать в реальной текущей админке при малейшем сомнении (см. п.1 — минимум 2 расхождения между
документами разрешаются именно так).

## 7. Что НЕ делать

- Не пытаться механически восстановить оригинальные имена файлов/модулей через `webcrack` —
  уже проверено в этой сессии: де-бандленный вывод (1342 файла с числовыми именами) даёт читаемый
  код, но не даёт структуру проекта автора. Полезен только как разовый справочник для чтения
  конкретной логики (например, найти как разрешается `?object=streams.export`, п.1.2), не как
  основа новой сборки.
- Не переписывать весь React-слой сразу (см. §4) — начать с сохранения моста.
- Не "исправлять" зашитые опечатки/инверсии контракта (`ingore_prefetch`,
  `cookies_enabled`/`disable_stats`) без синхронного изменения бэкенда — иначе сохранение
  соответствующих настроек тихо сломается.
