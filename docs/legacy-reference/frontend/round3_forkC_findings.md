## Найденные и исправленные баги

### 1. `TrafficSourceRepository.php` — `$_postbackStatuses = NULL`
Классический паттерн "never-populated array constant, used in foreach". `getPostbackStatuses()` (экшен `trafficSources.postbackStatuses`, используется в настройке постбека конкретного источника трафика — см. баннер на вкладке "S2S Postbacks" кампании: "чтобы отправить постбек источнику, используйте опцию Postback в настройках источника") кидал `Invalid argument supplied for foreach()`. Исправлено — заполнен константами `POSTBACK_STATUS_SALE/LEAD/REJECTED/REBILL` (уже объявленными в том же классе, просто не собранными в массив).

### 2. `CronTaskStatus.php` — `getExecutedAt()` не кастовал строку в DateTime
**Критично.** Модель `cron_status` хранит `executed_at` как DATETIME, но геттер отдавал сырую строку. Любая cron-задача, чей `isReady(\DateTime $executedAt)` строго типизирован (например `CheckTsTask`), падала с `TypeError: ... must be an instance of DateTime, string given` — но **только если для этой задачи уже существует строка статуса в БД** (первый когда-либо запуск проходил нормально, т.к. использует дефолтный `new DateTime("-999 days")` из памяти, не из БД). Поскольку исключение необработанное, оно прерывало **весь** `CronTaskRunner::runTasks()` foreach — то есть одна битая задача блокировала вообще все последующие cron-задачи в этом запуске. Исправлено: `getExecutedAt()` теперь оборачивает строку в `new DateTime($value)`.

### 3. `Bootstrap::initCacheService($rootFolder = false)` — неверный дефолт параметра
**Самый серьёзный баг сессии по своим последствиям.** Все 3 места вызова (`Bootstrap.php` дважды, `SettingsService.php`) вызывают без аргумента, поэтому `$rootFolder` всегда был `false` → PHP кастует в `""` → путь кэша получался `/cache` (корень контейнера), а не `ROOT/cache` (`/app/cache`). На **вебе** это не проявлялось, потому что дев-сервер запускается от `root`, а `/cache` создаётся и пишется от root без проблем. Но `cron:run` **обязан** выполняться от `www-data` (есть explicit-проверка "User 'root' can't run this command"), а `www-data` не может писать в root-owned `/cache` → `Doctrine\Common\Cache\FileCache` кидал `InvalidArgumentException: The directory "/cache" is not writable.` — **на каждом единственном запуске cron, без исключений**, с самого начала существования этого дев-стенда. Это и есть корневая причина того, что вся статистика (Dashboard/Reports/Clicks log) всегда показывала "No data" несмотря на реальные клики — cron физически ни разу не отрабатывал полностью. Исправлено: `$rootFolder = ROOT`.

### 4. `Traffic\CommandQueue\Service\DelayedCommandService::pop()` — не возвращал результат
Ещё один классический "потерянный return" — метод декодировал элементы очереди через `json_decode()`, но никогда не собирал их в массив и не возвращал. `popAll()`/`ProcessCommandQueue::process()` получали `NULL` вместо списка команд. Исправлено — собирается `$result[]` и возвращается.

### 5. `Traffic\CommandQueue\QueueStorage\FileStorage::pop()` — то же самое, но ещё и **разрушительно**
Метод читает файл очереди построчно, ничего не собирает и не возвращает, а затем **удаляет** файл очереди (`_endDequeue()` → `unlink()`) — то есть при каждом вызове реально уничтожает необработанные данные без единого шанса их прочитать. Актуально для инсталляций с `draft_data_storage = file` (не наш стенд, у нас Redis — см. ниже, — но это реальный баг, который проявится у любого, кто использует файловое хранилище очереди). Исправлено — собирается и возвращается результат.

### 6. `Traffic\CommandQueue\QueueStorage\RedisStorage::pop()` — бесконечный цикл + не возвращал результат
**Найден и исправлен ПАРАЛЛЕЛЬНО другим форком** (файл поменялся на диске во время моей работы над ним — не стал перезаписывать, финальная версия на диске корректна). Оригинал: `while (true) { ...; if (не пусто) { decode но не собирать } }` — при пустом результате нет `break`, при непустом результат `_decode()` выбрасывается. И бесконечный цикл, и отсутствие возврата. **Это фактический бэкенд этого стенда** (`draft_data_storage=redis`, подтверждено дебагом: `push()` создаёт `RedisStorage`, не `FileStorage`).

## Нерешённая часть той же цепочки (важно, оставляю для следующей сессии)

После исправления пунктов 3, 4, 6 (и параллельного фикса 6 другим форком) **клики всё ещё не появляются в `tds_clicks`** после полного, безошибочного прогона `cron:run`. Проверено: `push()` в `DelayedCommandService` реально вызывается и не падает; `RedisStorage` — подтверждённый активный бэкенд; `cron:run` теперь отрабатывает **без единой ошибки** в логе (только безобидные `[FileStorage] no key 'TRINFO'/'DOMAINS'/... That's ok` — это geo/campaign кэш-промахи, полёт нормальный) — но `tds_cron_status` тоже не обновляется для `ExecuteDelayedCommand` (только одна строка `CheckTsTask` с очень старой датой). Также обнаружена **отдельная особенность окружения**: `var/locks/*.lock` файлы (flock-based) не освобождались между запусками `cron:run` даже после того, как держащий их PHP-процесс уже завершился — пришлось руками удалять `var/locks/cron.lock.lock`/`delayed_command.lock` перед каждым повторным запуском, иначе получаем "Another cron process is already running. Skipping." Это похоже на известную проблему `flock()` на bind-mount томах Docker Desktop для macOS (файловая система хоста через gRPC-FUSE/virtiofs) — стоит проверить на **реальном Linux-сервере**, там `flock()` должен работать штатно.

**Куда копать дальше** (сузил круг подозреваемых, чтобы не переделывать всю диагностику с нуля):
1. Проверить, что Redis-соединение (host/port/db index/prefix) идентично между web-контекстом (клик, `push()`) и CLI-контекстом (`cron:run`, `pop()`/`count()`) — `RedisStorageService::instance()->prefix()` используется вручную в `pop()`/`count()` через прямой `multi()`, а `push()` идёт через `rPush()` того же `_redisService` — если у обёртки есть автопрефиксация, а `multi()` её обходит (или наоборот) — ключи могут не совпадать.
2. Проверить `DelayedCommandRepository::find("add_click")` — резолвится ли имя команды в `AddClickCommand` корректно (регистрация в Initializer).
3. Проверить `Component\Clicks\ClickProcessing\Pipeline::process()` — отдельный пайплайн (не путать с `Traffic\Pipeline\Pipeline`), непосредственно пишущий в `tds_clicks` — возможно там ещё один баг того же класса (не проверялся из-за нехватки времени).
4. Убедиться, что `tds_cron_status` вообще обновляется хоть для одной задачи после моих фиксов — если нет **вообще ни для одной**, значит проблема ещё выше по стеку (возможно `CronTaskStatusService::updateStatus()` сам ломается, или `$cronTask->isReady()` возвращает false для всех задач по не найденной пока причине).
